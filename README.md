# ExiQO Migrate

ExiQO Migrate takes a TIBCO BusinessWorks estate (BW5 `.process` and BW6 `.bwp`) through seven
steps (Upload, Discover, Validate, Design, Build, Verify, Deploy) to a generated .NET 10 service
with its tests and its Azure infrastructure code. Each step shows the evidence behind its status,
and the human gates G1 to G6 are decided by named users, never by an agent.

The demo estate in `samples/synthetic-gmf/` is synthetic. Parity results are derived from the
TIBCO model by the platform's evaluator; no TIBCO engine runs in this build.

## Repository layout


| Path                     | What it holds                                                                                                                                                                                                                                               |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `engine/`                | Python: TIBCO parser and neutral model (`tibco_parser`, `ir`), domain discovery, static analysis, agents, knowledge layer, parity evaluator, .NET generator and runner (`dotnet_gen`), infrastructure generator (`infra_gen`), with tests in `engine/tests` |
| `api/`                   | FastAPI service: routers per tab, job runner with streamed events, gates and audit, Alembic migrations, with tests in `api/tests`                                                                                                                           |
| `web/`                   | Next.js app: the seven-tab stepper plus Settings, History and Readiness; Playwright specs in `web/e2e`                                                                                                                                                      |
| `samples/synthetic-gmf/` | the synthetic GM Financial estate (generated by `make samples`)                                                                                                                                                                                             |
| `samples/public/`        | public TIBCO sample sets, used only for parser tests (see its README for licenses)                                                                                                                                                                          |
| `scripts/`               | synthetic estate generator, BW6 structure check, toolchain probe, acceptance script `demo_check.py`                                                                                                                                                         |
| `deploy/`                | Postgres init script for Docker Compose                                                                                                                                                                                                                     |
| `docs/`                  | `DEMO.md` (demo runbook), `TOOLCHAIN.md` (local tools and network constraints), `superpowers/` (design spec and implementation plan)                                                                                                                        |




## Setup

Requirements: Python 3.11 or later, Node 22, PostgreSQL 16 with pgvector, the .NET 10 SDK, Terraform (or
OpenTofu) and Terragrunt. `make toolchain` reports what it finds; `docs/TOOLCHAIN.md` explains
how the tools were installed in the build container.

```sh
cp .env.example .env      # then fill in what you need (see below); never commit .env
make setup                # .venv with the engine and API, and npm install in web/
make db                   # Postgres through Docker Compose when a daemon runs, then alembic upgrade head
make samples samples-zip  # the synthetic estate and samples/synthetic-gmf.zip
make api                  # API on http://localhost:9000 (change API_PORT in .env to move it)
make web                  # web on http://localhost:3000
```

Without a Docker daemon, `make db` uses the Postgres at `DATABASE_URL`: create the `exiqo` role
and the `exiqo` and `exiqo_test` databases first (migration memory lives in Neo4j, so Postgres
needs no extension).

## What runs with no keys

With `PROVIDER=fake` and `EMBEDDINGS_BACKEND=hash` the whole flow runs offline and
deterministically: parsing, domain discovery, static risk rules, citation verification,
coverage, the scripted analyst, risk reviewer, challenger, designer, test engineer and builder
replies, scaffolding, test generation, infrastructure generation and validation, the parity
evaluator and the plan in connect-later mode. The screens say that the fake provider is active.
With no provider at all (`PROVIDER=auto` and no keys), the code-only paths still run and the
analysis is labeled code-only.

What always needs the network: NuGet for `dotnet restore` (or the offline cache from
`make nuget-cache`), the Terraform or OpenTofu provider registry for `terraform validate`, and an
Azure subscription for a real plan. The generated tests need a Postgres: export
`TEST_DATABASE_URL` (the build passes it to them) or run Docker Desktop, because with it empty
they start a Testcontainers `postgres:16-alpine`, which needs a Docker daemon and, on the first
run, a Docker Hub pull.

### Connectors (local fakes)

GitHub, Confluence, Jira and Figma integrations are off by default. To try them without any real
service, run the fakes and use the settings it prints:

```sh
python scripts/fake_connectors.py
```

It serves a fake GitHub, Confluence, Jira and Figma on loopback ports, writes token files to a
temporary directory and prints the `CONNECTORS` and `*_FILE` variables to start the API with.
`python scripts/demo_check.py --only connectors` then runs the connection tests (it prints
`connectors: SKIP (none enabled)` when none is on); `--publish --github-repo <owner>/<repo>` in a
full run also pushes, publishes a page and creates an issue. Installing them for real is in
`docs/deploy/GMF-INSTALL.md` ("Connectors") and `docs/deploy/RUNBOOK.md`.

## Tests

```sh
make test   # engine/tests and api/tests; needs Postgres at TEST_DATABASE_URL
make e2e    # needs a migrated DATABASE_URL; regenerates the synthetic zip first
```

`make test` reads `TEST_DATABASE_URL` (default `postgresql://exiqo:exiqo@localhost:5432/exiqo_test`).
When the role cannot create databases, set `SCENARIO_DATABASE_URL` to the same test database.
Tests that need NuGet skip with the reason when it is unreachable.

`make e2e` starts the API (fake provider, hash embeddings) and the web on two free ports and
refuses a busy port rather than reusing a server it did not start; set `E2E_API_PORT` and
`E2E_WEB_PORT` to choose the ports, and `E2E_REUSE_SERVERS=1` to reuse servers you started
yourself. The build, verify and deploy spec probes the finished build: when restore passes it
follows the success path (service, Swagger, dev token, parity); when restore fails it asserts the
failure states on every screen.

## Acceptance script

`make demo-check` runs `scripts/demo_check.py` against the API at `API_URL`, or starts one on
`API_PORT` for the run (fake provider unless `PROVIDER` is set or a Claude token or Azure OpenAI
key is configured; hash embeddings unless `EMBEDDINGS_BACKEND` is set) and stops it afterwards.
It creates a project, uploads the synthetic zip, scans, discovers, analyzes `DealerFundingRequest`
and `CreditApplicationIntake`, approves G1 to G3 as `sme.vicky` and `architect.lee`, builds,
checks the infrastructure, verifies, runs the plan in connect-later mode and checks test data
masking, readiness and the audit trail. It prints a pass/fail table and exits non-zero on any
failed row.

A `connectors` step runs the enabled connectors' connection tests (skipped when none is enabled; the tests need `admin`).

A `memory` step checks the project memory: available, a revision per
content phase, lineage and search for each target, a non-empty latest diff, a curation note as
`sme.vicky` that lands as a new revision, and an answer that cites a memory node.

It probes NuGet (or the offline cache) and the provider registry first and runs in one of two
modes, named at the top of the table with the reason:

- `full` (both probes pass): every test green, infrastructure validated, the service started,
parity 100% on the generated scenarios except the intended fields tied to findings decided Fix.
- `offline` (a probe failed): the same flow asserting the honest failure states: restore failed
with the NuGet reason and the `make nuget-cache` remedy, build and test skipped, G4 not
enabled, the service not running and verify refused, the registry reported unreachable.

Force a mode with `make demo-check DEMO_ARGS="--mode full"` (or `--mode offline`).

Against an installed platform (the smoke test in the install guide) run the script directly:
`scripts/demo_check.py --base-url https://<host>` talks to the API under `<host>/api`, and `--token`
(or `EXIQO_TOKEN`) sends an Entra access token for an `AUTH_MODE=oidc` install. Without those flags
it behaves as described above.

## Memory

Each project keeps a versioned memory in Neo4j: the estate, analyses, designs, builds and the
decisions people take, linked from legacy process to generated code, and every change creates a
numbered revision. Search, Ask and the generation steps read from it. `make neo4j` starts the
local database (set `NEO4J_URI` and its credentials in `.env`); the API and workers ingest into it
after each phase. Open the **Memory** explorer in the web app to search, browse the graph and
lineage, step through revisions and diffs, and add curations (notes, mapping corrections,
obsolete marks) as an SME or admin; viewers read only. `make demo-check` has a `memory`
step that exercises all of this.

## ExiQoian

ExiQoian is the project assistant, opened from the top bar on every project screen (or Ctrl+J and
Cmd+J) by every persona, viewers included. It answers only about the current project, its TIBCO
workflows, the modernized application and what each phase found, from the project's memory, with a
citation chip after each sentence it supports (hover for the artifact, click to open it). It
declines everything else, and any text that tries to change how it works, with a fixed reply and
no model call; it takes no actions. It needs the Neo4j memory and works with or without a model
provider. `make demo-check` has an `exiqoian` step after `memory`: as `sme.vicky` it asks "What
does DealerFundingRequest do?" and requires an answer with at least one citation, then asks "what
is 2+2" and requires the off-topic decline. Operating notes (conversation privacy, the
`exiqoian asked` audit row, the rate limit) are in `docs/deploy/RUNBOOK.md`, "ExiQoian".
