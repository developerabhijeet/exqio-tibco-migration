# Install ExiQO Migrate on GM Financial's AKS

This guide takes a platform engineer from an empty namespace to a working install in GM
Financial's own Azure tenant. It describes what the chart, the Terraform and the pipelines in
this repository actually do. Two companion guides cover the rest:

- `DEPLOY-STEP-SECRETS.md`: the identities the Deploy step uses to plan infrastructure in target
  subscriptions.
- `RUNBOOK.md`: day-two operations (scaling, stuck jobs, backups, rotation, upgrades).

The pieces:

| Piece | Where | What it is |
|---|---|---|
| Chart | `deploy/helm/exiqo` | api, web and worker Deployments, Neo4j, NetworkPolicies, the migration hook |
| Prerequisites (optional) | `deploy/azure` | Terraform for ACR, Key Vault, identities, Postgres, Azure Files, backup storage. Reference: `deploy/azure/README.md` |
| Release pipelines | `deploy/pipelines` | build, scan, sign, deploy for Azure DevOps and GitHub Actions |
| Images | `deploy/docker` | the two Dockerfiles, and `deploy/docker/compose.pilot.yml` for a single-VM pilot (not covered here; its header lists its secrets) |

Conventions: one install per namespace. Resource names are fixed (`exiqo-api`, `exiqo-worker`,
`exiqo-migrate`, `exiqo-neo4j`), whatever the Helm release is called, because the Workload Identity
federated credentials name the service accounts. Examples use the namespace `exiqo` and the
release name `exiqo`.

**Dry run first.** The signing path (cosign with a Key Vault key) and the Helm deploy with Entra
sign-in to AKS were verified by tests and rendering only, never against a real Azure tenant. Run
the whole procedure once in a non-production namespace and subscription before the first
production install, and expect to adjust names, firewall rules and role assignments.

## 1. Prerequisites checklist

On the AKS cluster:

- [ ] OIDC issuer and Workload Identity enabled. Read the issuer URL for the federated credentials:

  ```sh
  az aks update -g <aks-rg> -n <aks> --enable-oidc-issuer --enable-workload-identity
  az aks show -g <aks-rg> -n <aks> --query oidcIssuerProfile.issuerUrl -o tsv
  ```

- [ ] The Secrets Store CSI driver with the Azure Key Vault provider (the AKS add-on
  `azure-keyvault-secrets-provider`). The chart relies on its secret sync (`secretObjects`) for the
  Neo4j password, so the add-on's default (sync on) must stay on.
- [ ] The Azure Files CSI driver (an AKS default) and the `managed-csi-premium` StorageClass (the
  Neo4j volume; change `neo4j.volumes.data.dynamic.storageClassName` if GMF uses another).
- [ ] An ingress controller. `ingress-nginx` in the namespace `ingress-nginx` works as is
  (`networkPolicy.ingressNamespaces`). With Application Gateway (AGIC), set `ingress.className`
  and the annotations shown in `values.yaml`, and put the gateway subnet in
  `networkPolicy.ingressCidrs`.
- [ ] etcd encryption at rest with a customer-managed key (KMS). The Neo4j initial password is
  synced into a Kubernetes Secret and therefore lives in etcd.
- [ ] A way to run `helm` 3.16 and `kubectl` against the cluster, and an identity allowed to
  install into the namespace. See the deployer's role in section 7.

In the subscription (create with `deploy/azure` or bring your own):

- [ ] Azure Container Registry for the images.
- [ ] Key Vault in RBAC mode, reachable from the cluster (private endpoint or firewall rule).
- [ ] PostgreSQL flexible server 16 with the `VECTOR` extension allow-listed (`azure.extensions`),
  databases `exiqo` and `exiqo_test`, and an administrator login that may create extensions and
  databases (the parity step creates one `exiqo_scn_<project>_test` database per project).
- [ ] An Azure Files Premium share for `DATA_DIR` (uploads and generated solutions).
- [ ] A Blob container for Neo4j dumps, only if you turn the backup on (section 9).
- [ ] An Azure OpenAI resource with deployments for the strong, standard and efficient tiers.
- [ ] A DNS name for the ingress host and a TLS certificate as a Secret in the namespace
  (`ingress.tlsSecretName`).
- [ ] Rights to create an Entra app registration and groups (section 3).

Terraform for most of this is in `deploy/azure`; read `deploy/azure/README.md` for the switches,
the role assignments it makes, and the `helm_values` output it produces. In short:

```sh
cd deploy/azure
cp gmf.example.tfvars gmf.tfvars          # GMF's names and ids
terraform init -backend-config=...         # see the README for the backend settings
terraform plan -var-file=gmf.tfvars -out=prereqs.plan && terraform apply prereqs.plan
terraform output -json helm_values > values.azure.json
```

Two cautions from that README: the PostgreSQL password is generated by Terraform and written to
Key Vault, so the Terraform state contains it (keep the state container private and encrypted);
and the AKS cluster identity needs Storage Account Contributor on the data account (the README
lists the variable that grants it) because the Azure Files CSI driver reads the account key.
`make azure-validate` checks the Terraform without Azure credentials.

Network facts to settle with GMF's network team now:

- The platform pods (api, worker, migration hook) need egress to Postgres (5432), Key Vault, Entra
  ID, Azure Resource Manager, Azure OpenAI, and GMF's package mirrors. The chart's NetworkPolicies
  restrict by address and port; host names are enforced by GMF's Azure Firewall or egress gateway.
  `egress.fqdns` lists the names to allow (section 6).
- Nothing else is allowed. Claude stays off unless `providers.claude.enabled` is true, and then its
  hosts (`*.anthropic.com`) must be added to the firewall.

### Without Terraform: the platform identity and its grants

If you skip `deploy/azure` (or its `enable_identities` switch), create these by hand **before the
first `helm upgrade`**. The pre-install hook mounts Key Vault with the `exiqo-migrate` account, so
its credential must exist before the hook runs.

- [ ] The user-assigned managed identity `exiqo-platform`. Its client ID is
  `identity.platformClientId`.

  ```sh
  az identity create -g <identity-rg> -n exiqo-platform
  az identity show -g <identity-rg> -n exiqo-platform --query '{clientId:clientId, principalId:principalId}'
  ```

- [ ] A federated credential on it for every service account that uses it. The issuer is the
  cluster's OIDC issuer URL, the audience `api://AzureADTokenExchange`, and each subject is exact
  (`system:serviceaccount:<namespace>:<account>`):

  | Service account | Used by |
  |---|---|
  | `exiqo-api` | api pods |
  | `exiqo-worker` | worker pods |
  | `exiqo-migrate` | the migration hook Job |
  | `exiqo-neo4j` | the Neo4j pod (it mounts the Key Vault object `exiqo-neo4j-auth`); only with `neo4j.enabled` |
  | `exiqo-neo4j-backup` | the backup CronJob; only with `neo4jBackup.enabled`, and unless `identity.backupClientId` names another identity |

  ```sh
  issuer="$(az aks show -g <aks-rg> -n <aks> --query oidcIssuerProfile.issuerUrl -o tsv)"
  for sa in exiqo-api exiqo-worker exiqo-migrate exiqo-neo4j; do
    az identity federated-credential create -g <identity-rg> --identity-name exiqo-platform \
      --name "$sa-exiqo" --issuer "$issuer" --subject "system:serviceaccount:exiqo:$sa" \
      --audiences api://AzureADTokenExchange
  done
  ```

  The web pod uses no identity. Each deploy identity gets a credential for `exiqo-worker` only
  (`DEPLOY-STEP-SECRETS.md`). The chart's install notes print the same list for your values.

- [ ] Key Vault Secrets User for `exiqo-platform` on the vault (`keyVault.name`).
- [ ] AcrPull for the cluster's kubelet identity on the registry.
- [ ] Cognitive Services OpenAI User for `exiqo-platform` on the Azure OpenAI account, when
  `providers.azureOpenAI.auth` is `managed_identity`. The Terraform path grants this only when
  `azure_openai_account_id` is set, so check it there too.
- [ ] With the Neo4j backup on: Storage Blob Data Contributor on the backup container for the
  backup identity (`identity.backupClientId`, default `exiqo-platform`).

```sh
pid="$(az identity show -g <identity-rg> -n exiqo-platform --query principalId -o tsv)"
az role assignment create --assignee-object-id "$pid" --assignee-principal-type ServicePrincipal \
  --role "Key Vault Secrets User" --scope <key vault resource id>
az role assignment create --assignee-object-id "$pid" --assignee-principal-type ServicePrincipal \
  --role "Cognitive Services OpenAI User" --scope <azure openai resource id>
```

## 2. Mirror images and toolchains

### Images

The cluster pulls images by digest only (the schema rejects tags). Four images are involved:

| Image | Values key | Source |
|---|---|---|
| ExiQO platform (api, worker, migration) | `image.platform.repository`, `image.platform.digest` | built from `deploy/docker/platform.Dockerfile` |
| ExiQO web | `image.web.repository`, `image.web.digest` | built from `deploy/docker/web.Dockerfile` |
| Neo4j | `neo4j.image.customImage` | `docker.io/library/neo4j:5.26.32@sha256:...` in `values.yaml` |
| Azure CLI (Neo4j backup only) | `neo4jBackup.azureCliImage` | `mcr.microsoft.com/azure-cli:...@sha256:...` in `values.yaml` |

Point all four at GM Financial's registry. For Neo4j and the Azure CLI image, import the pinned
image into the registry and override the key with the mirror's reference plus the same digest (a
digest is the same whichever registry serves it). The Neo4j Helm chart (a subchart, pinned in
`Chart.lock`) is fetched from `https://helm.neo4j.com/neo4j` at build time of the chart's
dependencies. `Chart.yaml` names that repository by URL, so `helm repo add` of a mirror does not
redirect `helm dependency build`: mirror the chart and pull it from the mirror yourself, as
`deploy/pipelines/release.sh` does with `NEO4J_CHART_REPOSITORY` (section 7 has the commands).

Build the two ExiQO images with the release pipeline (section 7), or by hand:

```sh
make images          # builds both images locally
make image-test      # UID 10001, read-only root, no package manager, offline embeddings
make image-lint      # hadolint
make image-scan      # Trivy, fails on CRITICAL (exceptions in .trivyignore)
make egress-audit    # hosts named in our code and in the web bundle versus the allowlist
```

The Dockerfiles take the base images and download sources as build arguments so nothing is pulled
from a public site: `BASE_IMAGE_DOTNET`, `BASE_IMAGE_UV`, `BASE_IMAGE_NODE_BUILD`,
`BASE_IMAGE_NODE_RUNTIME` (mirrored images, by digest), `PIP_INDEX_URL`, `HF_ENDPOINT`,
`NPM_CONFIG_REGISTRY`, `TERRAFORM_BASE_URL` and `TERRAGRUNT_BASE_URL`.

**Never put credentials in these URLs.** Build arguments persist in the image history, so a mirror
URL such as `https://user:token@mirror/...` would ship the token inside the image. Use mirrors
that the build agents can reach without credentials in the URL (network allow-listing, or a
credential helper configured on the agent).

### Package mirrors for the generated code

The platform builds the .NET services it generates and plans their Terraform, so the worker pods
need GMF's package mirrors at runtime. They are configured, not hard-coded:

| Values key | Becomes | Used for |
|---|---|---|
| `mirrors.nuget` | `NUGET_SOURCE` | the feed written into each generated `nuget.config` |
| `mirrors.npm` | `NPM_CONFIG_REGISTRY` | npm installs |
| `mirrors.terraformConfig` | `TF_CLI_CONFIG_FILE` (mounted at `/etc/exiqo/terraform.rc`) | a `provider_installation` network mirror for Terraform providers |

Mirror URLs must be https. The worker's NuGet cache is per pod (`worker.nugetCacheSize`) and is
refilled from the mirror after a restart.

GMF adds its own mirror hosts in two places: `egress.fqdns` (the firewall list, shown in the
About panel) and, for the build-time audit, `deploy/egress-allowlist.txt` if GMF runs `make
egress-audit` on images that name those hosts.

### The generated CI templates

The Azure DevOps and GitHub workflows the platform generates for the migrated services download
Terraform from `releases.hashicorp.com` and Terragrunt from `github.com`. They run on GMF's CI
agents, not in the platform's pods, which is why those two hosts are in the allowlist file. Behind
a strict proxy, edit the generated pipeline (or the templates
`engine/infra_gen/templates/azure-pipelines.yml.j2` and
`engine/infra_gen/templates/github_workflow.yml.j2`) to download from GMF's mirror.

### What the egress audit does and does not catch

`make egress-audit` is build-time evidence, not enforcement. It lists hosts named in our own code
(`/app` of the platform image) and in what the web image ships to the browser, and fails on any
that is not in `deploy/egress-allowlist.txt`. Its limits:

- URLs with a scheme are always checked, but a bare host name (no scheme) is recognized only with a
  common top-level domain (`com`, `net`, `org`, `io`, `ai`, `dev`, `app`, `cloud`, `co`, `us`,
  `gov`, `edu`). A host with another TLD that appears without `https://` is not seen.
- A host assembled at runtime (string concatenation, a template such as `https://${host}`) is not
  seen; only literals are.
- PascalCase dotted names such as `Microsoft.AspNetCore.App` are treated as identifiers, not hosts.
- Third-party runtimes (the Python virtualenv, the .NET SDK, the web server's `node_modules`) are
  out of scope.

Runtime egress is enforced by the NetworkPolicies in the chart (addresses and ports) and by GMF's
Azure Firewall FQDN rules (names). Treat the audit as the check that the code does not name an
unexpected host, and the firewall as the control.

## 3. Entra app registration and role groups

The platform signs users in with Entra ID (authorization code with PKCE) against an app
registration in GMF's tenant. The API holds the sign-in: the browser never holds a token, only a
signed session cookie.

### Register the application

```sh
az ad app create --display-name "ExiQO Migrate" --sign-in-audience AzureADMyOrg \
  --web-redirect-uris https://<ingress.host>/api/auth/callback
```

- The redirect URI is `https://<ingress.host>/api/auth/callback`, with https. The chart sets
  `OIDC_REDIRECT_URI` to exactly that. Do not override it with an http address: behind the
  TLS-terminating ingress the API sees plain http, and Entra rejects a redirect URI that is not
  registered.
- The scopes are `openid profile email`. No Microsoft Graph permission and no admin consent are
  needed: the platform never calls Graph.
- The example install uses a confidential client: a client secret for the app, stored in Key Vault
  as `exiqo-oidc-client-secret` (`keyVault.secrets.oidcClientSecret`). Client secrets expire
  (24 months at most): record the expiry and rotate before it (section 10). A public client
  (no secret, `oidcClientSecret` left empty) needs the redirect URI registered under "Mobile and
  desktop applications" with public client flows allowed; that path has not been exercised.
- `auth.tenantId` must be the tenant GUID, not a domain name (the schema enforces it). The token
  issuer the API accepts is `https://login.microsoftonline.com/<tenantId>/v2.0`. `auth.clientId` is
  the application (client) ID.

### Token version

The browser sign-in validates the ID token from the v2.0 endpoint. Bearer access tokens (used by
`scripts/demo_check.py --token` and any automation) are accepted only if they are v2.0 tokens, so
set the app's access token version to 2 (`accessTokenAcceptedVersion` in the manifest; in the
Microsoft Graph form of the manifest it is the `requestedAccessTokenVersion` property of the `api`
object):

```sh
az ad app update --id <appId> --set api.requestedAccessTokenVersion=2
```

A v1.0 token (issuer `https://sts.windows.net/<tenant>/`) is refused with "wrong issuer". Bearer
tokens may be issued for the client ID or for `api://<clientId>`.

### Roles

Seven role keys exist; `auth.roleGroups` maps each to Entra group object IDs and/or app role
values:

| Key | Holds |
|---|---|
| `admin` | the About panel, Settings and history writes |
| `viewer` | read only, every screen |
| `sme` | decides gates G1 and G2 |
| `architect` | decides gate G3 |
| `engineer` | decides gate G4 |
| `qa` | decides gate G5 |
| `ops` | decides gate G6 |

Any role other than `viewer` may also write. A user who signs in but matches no role gets "your
account holds no ExiQO Migrate role" (HTTP 403). Gate decisions and audit entries record the
user's Entra object ID and user principal name.

Two ways to carry roles in the token (use either or both; the example mixes them):

1. **App roles (recommended).** Define app roles on the registration (for example `Exiqo.Sme`),
   assign groups or users to them on the enterprise application, and list the role values:

   ```yaml values
   auth:
     roleGroups:
       sme: [1a2b3c4d-0000-4000-8000-000000000003, Exiqo.Sme]
   ```

   ```sh
   az ad app update --id <appId> --app-roles @approles.json
   ```

   Set the enterprise application's "Assignment required" to yes, so only assigned users can sign
   in at all.
2. **Group IDs.** Set the groups claim to the group object ID and list the groups:

   ```sh
   az ad app update --id <appId> --set groupMembershipClaims=ApplicationGroup
   ```

   `ApplicationGroup` emits only the groups assigned to the application. `SecurityGroup` emits
   all of the user's security groups.

**Use app roles when users can be in many groups.** Entra leaves the `groups` claim out of a token
whose user is in more groups than it will list (about 200 in a JWT) and points at Microsoft Graph
instead. The platform does not call Graph, so for such a user only the `roles` claim counts, and
the API logs "Entra group overage" with the user's object ID. Group-only mapping would then give
that user no role.

### Session behavior

- The session cookie `exiqo_session` is signed with `SESSION_SECRET` (HttpOnly, Secure,
  SameSite=Lax) and lasts 8 hours. **Roles are fixed in the cookie at sign-in**: a change to a
  user's groups or app roles takes effect at their next sign-in, up to 8 hours later.
- Sign-out (`POST /api/auth/logout`) clears only the platform cookie. The user's Entra session is
  untouched, so signing in again may be silent. On shared workstations, sign out of Entra as well.
- Rotating `SESSION_SECRET` signs everyone out.

### Known trust boundary: generated services in Verify

In the Verify step the platform starts the .NET service it generated, on the worker, and the
browser reaches that service's Swagger UI and API through a proxy on the platform's own origin
(`/api/builds/<id>/run/proxy/...`). JavaScript served by that service therefore runs on the
platform's origin and can call `/api/*` with the signed-in user's session cookie. The services
verified are generated from GMF's own estate, so the code is GMF's code; this is a known
boundary, not a sandbox. Restrict who holds the `engineer` role (the role that builds and
verifies), and do not run Verify on an estate GMF does not trust.

### Known trust boundary: generated code on the worker

The worker also runs generated code as its own user: `dotnet test` and `dotnet run` in Build and
Verify, and Terraform (with the generated providers and modules) in Deploy's plan. That code runs
with everything the worker pod holds:

- the secrets mounted at `/mnt/secrets` in the worker: `DATABASE_URL`, `TEST_DATABASE_URL`,
  `APP_SECRET`, `INTERNAL_TOKEN`, `NEO4J_PASSWORD`, and the model credentials
  (`AZURE_OPENAI_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `LANGFUSE_SECRET_KEY`) when they are
  configured, since the build agents call the model from the worker. The sign-in secrets
  (`SESSION_SECRET`, `OIDC_CLIENT_SECRET`) are mounted in the api only: the worker has its own
  SecretProviderClass, `exiqo-platform-worker`, without them;
- the projected Workload Identity token (`AZURE_FEDERATED_TOKEN_FILE`), which it can exchange
  with Entra for the platform identity (`exiqo-platform`: Key Vault Secrets User on the vault, and
  whatever else GMF grants it) and for **every** deploy identity, because each one trusts the
  `exiqo-worker` service account.

So size the deploy identities for planning only: Reader, or the narrow custom role of
DEPLOY-STEP-SECRETS.md (read actions, provider registration, and the data-plane reads a refresh
needs), never write actions or role-assignment rights; applying goes through GMF's pipeline with
its own identity. Give `exiqo-platform` nothing beyond what section 4 lists. As for Verify, the
code is generated from GMF's own estate and reviewed at the gates, and the same rule applies:
restrict the `engineer` role and do not build an estate GMF does not trust. Running the
untrusted execution (tests, the service, Terraform) in a separate pod with no mounted secret and no
platform identity is the planned hardening.

## 4. Key Vault secrets

Secrets live in GMF's Key Vault and reach the pods as files under `/mnt/secrets` through the CSI
driver. The app reads each from `<NAME>_FILE` when set, else `<NAME>`; the chart sets only the
`_FILE` form, so no secret value is ever in a pod spec, Helm values, image, log or job payload. The
pods authenticate to the vault with Workload Identity as `exiqo-platform`, which holds Key Vault
Secrets User on the vault. The object names below are the defaults of `keyVault.secrets.*`.

| Secret | Key Vault object (values key) | Owner | Reader | Rotation |
|---|---|---|---|---|
| `DATABASE_URL` | `exiqo-database-url` (`keyVault.secrets.databaseUrl`), `postgresql+asyncpg://<user>:<password>@<host>:5432/exiqo?ssl=require` | Terraform (`deploy/azure`) or the database team | api, worker, migration hook (its own SecretProviderClass) | change the server password, update the secret, restart api and worker |
| `TEST_DATABASE_URL` | `exiqo-test-database-url` (`keyVault.secrets.testDatabaseUrl`), a database whose name ends `_test` | same | worker | with the database password |
| `APP_SECRET` | `exiqo-app-secret` (`keyVault.secrets.appSecret`), a Fernet key | platform team | api, worker | see section 10: values encrypted with it become unreadable |
| `SESSION_SECRET` | `exiqo-session-secret` (`keyVault.secrets.sessionSecret`) | platform team | api only (not mounted in the worker) | signs everyone out |
| `INTERNAL_TOKEN` | `exiqo-internal-token` (`keyVault.secrets.internalToken`) | platform team | api, worker (bearer between them on port 9100) | restart api and worker together |
| `NEO4J_PASSWORD` | `exiqo-neo4j-password` (`keyVault.secrets.neo4jPassword`), the bare password | platform team | api, worker | together with the next row, with an `ALTER USER` (section 10) |
| Neo4j initial credentials | `exiqo-neo4j-auth` (`keyVault.secrets.neo4jAuth`), `neo4j/<the same password>` | platform team | the Neo4j pod, through the Kubernetes Secret the CSI driver syncs | together with the previous row |
| `OIDC_CLIENT_SECRET` | `exiqo-oidc-client-secret` (`keyVault.secrets.oidcClientSecret`), empty for a public client | Entra app owner | api only (the API runs the sign-in; the web pod and the worker hold no copy) | before the Entra secret expires |
| `AZURE_OPENAI_API_KEY` | (`keyVault.secrets.azureOpenaiApiKey`), omit with `providers.azureOpenAI.auth: managed_identity` | Azure OpenAI owner | api, worker | regenerate the key in Azure, new Key Vault version, restart |
| `CLAUDE_CODE_OAUTH_TOKEN` | (`keyVault.secrets.claudeCodeOauthToken`), only with `providers.claude.enabled` | platform team | api, worker | new version, restart |
| `LANGFUSE_SECRET_KEY` | (`keyVault.secrets.langfuseSecretKey`), only with `langfuse.enabled` | platform team | api, worker | new version, restart |

Terraform creates the two database URLs. Create the rest in the same vault, using the names in
`keyVault.secrets` (commands in `deploy/azure/README.md`, "Not created here"). Generated with
Terraform they would land in its state, so they are created by hand:

Each value goes through a mode-600 temporary file and `--file`, never `--value`, so no secret
appears in the process list or the shell history:

```sh
umask 077
f="$(mktemp)"
put() { az keyvault secret set --vault-name <vault> -n "$1" --file "$f" --output none; }

python3 -c 'import base64, os; print(base64.urlsafe_b64encode(os.urandom(32)).decode(), end="")' >"$f"
put exiqo-app-secret
openssl rand -hex 32 | tr -d '\n' >"$f";  put exiqo-session-secret
openssl rand -hex 32 | tr -d '\n' >"$f";  put exiqo-internal-token
pw="$(openssl rand -hex 24)"
printf '%s' "$pw" >"$f";            put exiqo-neo4j-password
printf 'neo4j/%s' "$pw" >"$f";      put exiqo-neo4j-auth

unset pw
shred -u "$f" 2>/dev/null || rm -f "$f"; unset f
```

Use a password without `/` (hex, as above): Neo4j splits the initial credentials at the first `/`.

PostgreSQL authentication is by password. Entra authentication for Postgres is a possible later
change; the app does not fetch Entra tokens for database connections, so do not disable password
authentication on the server.

`GET /readyz` fails (HTTP 503, "secrets: error: unreadable ...") when any configured `_FILE`
secret is missing or unreadable, so a failed mount keeps a pod out of service.

## 5. Deploy-step identities

The Deploy step runs `terragrunt ... plan` for the generated infrastructure against GMF's target
subscriptions. By default it uses Workload Identity: one user-assigned managed identity per target
environment (`exiqo-deploy-dev`, `exiqo-deploy-prod`, ...), each federated to
`system:serviceaccount:<namespace>:exiqo-worker`, with Terraform running as
`ARM_USE_OIDC=true`. No client secret is stored anywhere.

`deploy/azure` creates the identities and their federated credentials (one per entry of its
`deploy_environments` variable) but grants **no role on the target subscriptions**: what each
identity may touch is GMF's decision. Grant the narrowest role that works:

- The platform only plans; `apply` is not part of this build (it goes through the generated
  pipeline). Plan needs read access plus access to the Terraform state account.
- Lead with a custom role over Contributor. Include `*/register/action` (or the per-provider
  `<Namespace>/register/action` entries for the namespaces the generated modules use; the list is
  in `DEPLOY-STEP-SECRETS.md`), or disable provider auto-registration in the generated provider
  configuration. Without one of the two, the first plan can fail while the provider tries to
  register resource providers.
- Contributor scoped to a resource group is the fallback when a custom role is impractical.

The full procedure, with commands for the identity, the federated credential, both role options,
declaring the environment in `deploy.environments`, the Key Vault service-principal alternative and
rotation, is in `DEPLOY-STEP-SECRETS.md`. For the Helm values, each environment appears twice:

```yaml values
deploy:
  credentialMode: workload_identity
  environments:
    - name: dev
      subscription: 2c3d4e5f-6a7b-4c8d-9e0f-1a2b3c4d5e6f
      auth: workload_identity
identity:
  deployIdentities:
    dev: 0d9e8f7a-6b5c-4d3e-a2f1-0e9d8c7b6a50
```

## 6. Values walk-through

### Neo4j

- The chart installs one Community-edition instance (`neo4j.enabled`, default true). High
  availability clustering needs a Neo4j Enterprise licence held by GMF; the chart does not provide
  one.
- **Nothing writes to Neo4j yet.** The platform checks connectivity only; the graph memory arrives
  in a later release. `GET /readyz` reports Neo4j as `ok`, `down: <exception class>` or `disabled`,
  but does not fail readiness on it.
- The pod runs as UID 7474 with a read-only root filesystem and a Premium SSD volume
  (`managed-csi-premium`, 64 Gi).
- **Credentials.** The Neo4j chart reads its initial password from the Kubernetes Secret
  `exiqo-neo4j-auth`, which the CSI driver syncs from the Key Vault object
  `keyVault.secrets.neo4jAuth` while a pod mounts it. That puts the password in etcd, hence the
  etcd-encryption prerequisite. Neo4j applies the password **only on the first start of an empty
  data volume**; changing the Key Vault object later does not change the live password.
  Section 10 gives the rotation procedure.
- **Bolt TLS is off by default** (in-cluster traffic, restricted by NetworkPolicy). To enable it,
  create a Secret holding a certificate and key for `exiqo-neo4j`, set `neo4j.ssl.bolt`
  (`privateKey.secretName`, `publicCertificate.secretName` and the `trustedCerts` sources, per the
  Neo4j chart's values), set the server-side `dbms.ssl.policy.bolt.enabled` through `neo4j.config`,
  and set `neo4j.uri` to `bolt+s://exiqo-neo4j:7687`. The API must trust the certificate (use a
  certificate its image already trusts, or `bolt+ssc://` for a self-signed one). This path has not
  been exercised.
- **Backups are off by default** (`neo4jBackup.enabled`). Neo4j Community can dump only a stopped
  database, so the CronJob scales the StatefulSet to 0, runs `neo4j-admin database dump`, scales it
  back to 1 and uploads the dump to Blob with Workload Identity. Neo4j is down for that
  stop-dump-start window (about a minute while the graph is small), and `GET /readyz` shows
  `neo4j: down` during it without failing. Turn it on when a release starts storing data in Neo4j
  (section 9). If the backup pod dies between stop and start, run
  `kubectl -n exiqo scale statefulset exiqo-neo4j --replicas=1` (or run the next `helm upgrade`).

## 7. Install and upgrade

### Install by hand

```sh
kubectl create namespace exiqo
kubectl -n exiqo create secret tls exiqo-tls --cert=tls.crt --key=tls.key

# The Neo4j subchart: pull the archive Chart.lock pins from GMF's mirror. Do not run
# the dependency build command; Chart.yaml names the public repository by URL.
mkdir -p deploy/helm/exiqo/charts
helm pull neo4j --repo <GMF mirror of https://helm.neo4j.com/neo4j> --version 5.26.32 \
  --destination deploy/helm/exiqo/charts
# or, for an OCI mirror:
# helm pull oci://<registry>/<path>/neo4j --version 5.26.32 --destination deploy/helm/exiqo/charts
echo "c7402735f1a4219db507d6c2c40a5106154092d680c7ff564da3db3c120312d7  deploy/helm/exiqo/charts/neo4j-5.26.32.tgz" \
  | sha256sum -c -

helm upgrade --install exiqo deploy/helm/exiqo -n exiqo \
  -f values.gmf.yaml -f values.azure.json \
  --atomic --timeout 20m
```

`--atomic` rolls the release back if the upgrade fails; `--timeout 20m` is needed because the
migration hook can run up to 15 minutes (`migration.activeDeadlineSeconds` is 900) before the
rollout starts. The chart prints, at the end, the federated credentials it expects (issuer and
subject for each identity) and a check command.

What happens, in order:

1. A pre-install and pre-upgrade hook creates the service account `exiqo-migrate`, a
   SecretProviderClass holding only `DATABASE_URL`, and the Job `exiqo-migrate`, which runs
   Alembic to head. Logs: `kubectl -n exiqo logs job/exiqo-migrate`. The Job stays after success so
   its logs can be read; the service account and SecretProviderClass are removed.
2. The api (2 replicas), web (2 replicas) and worker (2 to 6 replicas) Deployments roll out
   behind PodDisruptionBudgets; Neo4j starts as a StatefulSet.
3. Probes: the api uses `/healthz` for liveness and `/readyz` for readiness (the pod serves them
   at its root; through the ingress they are `/api/healthz` and `/api/readyz`), the web pod `/`,
   and each worker `/internal/healthz` on port 9100.

Things that go wrong on a first install:

- **A namespace with its own default-deny baseline blocks the migration hook.** On a first
  install the chart's NetworkPolicies do not exist yet when the hook runs. If the namespace
  already carries a default-deny policy (an Azure Policy or a platform baseline), allow egress from
  the `exiqo-migrate` pods to Postgres (port 5432) and to DNS before installing. On upgrades the
  chart's own `exiqo-platform-egress` policy covers it.
- **The StorageClass is cluster-scoped.** The deployer needs cluster scope to create it, or the
  install sets `data.storageClass.create` to false with `data.storageClass.name` naming a class the
  platform team created beforehand with the same parameters and mount options (UID and GID 10001).
- The identities' federated credentials must exist first (issuer = the cluster's OIDC issuer URL;
  subjects `system:serviceaccount:exiqo:exiqo-api`, `exiqo-worker`, `exiqo-migrate`, `exiqo-neo4j`,
  and `exiqo-neo4j-backup` when the backup is on; the same subject for each deploy identity).

### Release pipelines (recommended)

`deploy/pipelines` holds two templates that do the same thing and call one script,
`deploy/pipelines/release.sh`: `azure-pipelines.yml` for Azure DevOps and `github-release.yml`
(copy to `.github/workflows/release.yml`) for GitHub Actions. Stages: build (hadolint, build, push
a candidate tag), scan (egress audit and Trivy), sign (SBOM attestation and cosign signature with a
Key Vault key, then the release tag), deploy (verify, then `helm upgrade --install --atomic
--timeout 20m` as above). Images move between stages by digest only. Setup, in
`deploy/azure/README.md` ("Release pipeline identities") and in the headers of the two templates:

- **Three identities, one per privilege**, so the approval and "sign only after the scan" rest on
  what each stage can do: build (AcrPush), signer (AcrPush and Key Vault Crypto User on the signing
  key) and deployer (AcrPull and an AKS role). Each is federated with an **exact** subject, no
  wildcards: on GitHub `repo:<org>/<repo>:environment:release-build`, `...:environment:release-sign`
  and `...:environment:production` (one credential per environment); in Azure DevOps a service
  connection each.
- **Pin the verification key outside the repository.** The deployer verifies signatures with the
  public key committed at `deploy/gmf/cosign.pub`, but only if its sha256 equals
  `COSIGN_PUBLIC_KEY_SHA256`. Set that value (the `cosign_public_key_sha256` Terraform output) as a
  variable of the GitHub `production` environment, or in the Azure DevOps variable group
  `exiqo-release-deploy` (bound to the Deploy stage, with an Approvals check). Deploy refuses when
  it is unset or differs.
- **Restrict who can create `v*` tags** (a tag ruleset on GitHub; the "Create tag" permission in
  Azure DevOps): the tag is what reaches the signer. Require approvals on the `production`
  environment or deploy service connection.
- **CODEOWNERS** (or required reviewers on Azure DevOps) on `deploy/gmf/cosign.pub` and
  `deploy/pipelines/`.
- **The deployer's AKS role is GMF's call.** Nothing is granted unless `deployer_aks_role` is set in
  `deploy/azure`. When it is, Terraform also grants Azure Kubernetes Service Cluster User Role
  (the pipeline runs `az aks get-credentials`). The role needs cluster scope if the chart creates
  the StorageClass; otherwise use a namespace-scoped role with `data.storageClass.create` set to
  false (`deploy/azure/README.md` has both options).
- **AzureCLI@2 task version.** `azure-pipelines.yml` pins `AzureCLI@2.282.2`. An Azure DevOps
  organization or Server that does not have that build needs the nearest version it has.
- **Offline signature verification.** The pipeline verifies with a local public key and without the
  public transparency log (`--insecure-ignore-tlog=true`), but `cosign verify` may still try to
  fetch public Sigstore TUF metadata on first use. On a runner with no internet access, allow that
  host or provide the TUF root offline; this has not been exercised.
- The tool images (hadolint, Trivy, syft, cosign, crane, Helm) and the Trivy databases come from
  GMF's mirror through `TOOL_REGISTRY`; the variables to set are listed at the top of each template.

### Upgrade and roll back

An upgrade is the same command with new digests (or a new pipeline run). The migration hook runs
first, so new pods start on the new schema. Roll back with:

```sh
helm history exiqo -n exiqo
helm rollback exiqo <revision> -n exiqo --wait
```

A rollback restores the previous Kubernetes objects, not the database: Alembic migrations are not
reversed. Check the release notes for migrations that older images cannot run on; for a destructive
one, restore Postgres from a point in time (section 9). `RUNBOOK.md` has the upgrade checklist.

## 8. Smoke test

First, the pods and the health endpoints:

```sh
kubectl -n exiqo get pods -l app.kubernetes.io/name=exiqo
curl -fsS https://<ingress.host>/api/readyz
```

`readyz` answers `{"postgres": "ok", "neo4j": "ok", "secrets": "ok"}` when healthy. In the app,
the About panel (admin role, Help & Support) shows the same checks, the image digests, the auth
mode and the egress allowlist, from `GET /api/system/status`.

Then the acceptance run, which drives the whole seven-step flow on the synthetic estate:

```sh
make setup                     # once: .venv with httpx and the tools
make samples samples-zip       # the synthetic estate and samples/synthetic-gmf.zip
export EXIQO_TOKEN=<an Entra access token, see below>
.venv/bin/python scripts/demo_check.py --base-url https://<ingress.host>
```

`--base-url` addresses the install (the API is at `<host>/api`). The token is read from the
`EXIQO_TOKEN` environment variable; `--token` also exists but is not used above, because command
lines are visible to other users. Either sends the token as a bearer. An `AUTH_MODE=oidc` install ignores the `X-User` persona header the local run uses, so
the token's user must hold the `sme`, `architect`, `engineer` and `ops` roles; the run checks that
first and records the gate decisions under that one user's name. Without `--token`, an oidc install
answers 401 and the script says so. Without either flag the script behaves as before, against the
local API.

To get a token for a test user, give the app registration an Application ID URI (`api://<clientId>`)
and a scope, authorize a client that can request it (for the Azure CLI, pre-authorize its client ID
on that scope), then:

```sh
az account get-access-token --scope api://<clientId>/.default --query accessToken -o tsv
```

The token must be a v2.0 token (section 3). This path has not been exercised against GMF's
tenant.

What to expect: the run takes tens of minutes, uses the install's Azure OpenAI deployments (real
model calls) and the worker's package mirrors, and leaves a project named `acceptance <time>` with
synthetic data in the install's database (this build has no project delete). The "Swagger answers"
check is skipped when a token is used, because the proxied Swagger UI is for browsers and reads the
session cookie, not a bearer. The run is `full` mode by default against an installed platform;
`--mode offline` asserts the honest-failure states instead.

## 9. Backup and restore

Postgres holds everything the platform stores today. The `DATA_DIR` share holds uploaded estates and
generated solutions. Neo4j holds nothing yet.

### Postgres (Flexible Server point-in-time restore)

Backups are automatic; the retention is `postgres_backup_retention_days` in `deploy/azure` (set
geo-redundant backup there if GMF requires it). A restore creates a **new server**:

```sh
az postgres flexible-server restore -g <rg> -n <new-server> \
  --source-server <server> --restore-time 2026-10-24T09:00:00Z
```

Then point the platform at it: update `exiqo-database-url` (and `exiqo-test-database-url`) in Key
Vault, set `postgres.host` and `postgres.cidrs` if they changed, run `helm upgrade`, and restart
the api and worker pods. If Terraform created the old server, import or replace it in state
rather than leaving the two to drift. Practice the procedure (`RUNBOOK.md`, restore drills) before
you need it.

### DATA_DIR (Azure Files)

Protect the `exiqo-data` share with Azure Backup for Azure Files (share snapshots). The
StorageClass has reclaim policy `Retain` and the claim is kept on uninstall, so deleting the release
does not delete the share. Restore the share to the same point in time as Postgres: rows reference
files under `/data/uploads` and `/data/builds`.

### Neo4j (dump and load)

Enable the backup when a release starts storing data in Neo4j:

```yaml values
neo4jBackup:
  enabled: true
  schedule: "30 2 * * *"
  storageAccount: stgmfexiqobackup
  container: neo4j-backups
networkPolicy:
  kubeApiCidrs: [10.50.0.4/32]
```

The CronJob stops Neo4j, dumps the store, starts Neo4j and uploads
`neo4j/<UTC timestamp>/neo4j.dump` to the container using `identity.backupClientId` (default: the
platform identity, which needs Storage Blob Data Contributor on the container; `deploy/azure`
grants it). Retention is the storage account's lifecycle policy. It needs the API server address in
`networkPolicy.kubeApiCidrs` and the account's blob host in `egress.fqdns`.

To restore, download the dump (`az storage blob download --auth-mode login`), scale Neo4j to 0
(`kubectl -n exiqo scale statefulset exiqo-neo4j --replicas=0`), run a one-off pod with the Neo4j
image and the claim `data-exiqo-neo4j-0` mounted at `/data` (subPath `data`), the dump at
`/backup/neo4j.dump`, as UID 7474, running `neo4j-admin database load neo4j --from-path=/backup
--overwrite-destination=true`, then scale Neo4j back to 1. `RUNBOOK.md` repeats this as a drill.
The procedure follows the Neo4j 5 manuals and has not been exercised in this repository.

## 10. Secret rotation

Mechanics: add a **new version** of the Key Vault secret (keep the same name). Pods read secrets
when they start, so a running pod keeps the old value until it restarts; a restarted pod mounts the
current version. With the CSI driver's rotation enabled (`--enable-secret-rotation` on the AKS
add-on, poll interval 2 minutes by default) the mounted file changes in place, but the app still
reads it only at start. So after every rotation, restart:

```sh
kubectl -n exiqo rollout restart deployment/exiqo-api deployment/exiqo-worker
```

Workers drain running jobs first (up to 570 seconds; the pod's grace period is 600), and rollouts
never take a pod down before its replacement is ready. The web pod holds no secret.

| Secret | Procedure |
|---|---|
| `DATABASE_URL`, `TEST_DATABASE_URL` | Change the password on the server, write the new URL to both Key Vault objects, restart api and worker. If Terraform owns the server, change the password through Terraform so state and vault agree. |
| `SESSION_SECRET` | New version, restart. Every user is signed out. |
| `INTERNAL_TOKEN` | New version, restart api and worker in one go. Until both sides have restarted, Verify calls from api to worker answer 401. |
| `APP_SECRET` | The Fernet key encrypts values the platform stores itself (an Azure OpenAI key entered in Settings, local-mode credentials). With managed identity and Workload Identity nothing important is stored, but a changed key makes anything already stored unreadable: re-enter those values after the change. |
| `OIDC_CLIENT_SECRET` | Create a second secret on the Entra app (`az ad app credential reset --append`), write it as a new Key Vault version, restart, then delete the old Entra secret. Do this before the expiry. |
| `AZURE_OPENAI_API_KEY` | Regenerate the second key in Azure, new version, restart, then regenerate the first. |
| Neo4j password | See below: two Key Vault objects change together, plus the live password. |

**Neo4j password.** `exiqo-neo4j-password` (the bare password) and `exiqo-neo4j-auth`
(`neo4j/<password>`) must always agree: the first is what the platform connects with, the second is
what a rebuilt data volume would be initialized with. Neo4j applies the initial password only on the
first start of the data volume, so changing the Key Vault objects alone changes nothing in the
running database. To rotate:

1. Change the live password: `kubectl -n exiqo exec -it exiqo-neo4j-0 -- cypher-shell -u neo4j`
   (it prompts for the current password), then
   `ALTER CURRENT USER SET PASSWORD FROM '<old>' TO '<new>';`.
2. Immediately write the new password to both Key Vault objects as new versions
   (`exiqo-neo4j-password` = the password; `exiqo-neo4j-auth` = `neo4j/<password>`).
3. Restart api and worker so they reconnect with the new password (until then `GET /readyz` shows
   `neo4j: down`, which does not take the pods out of service). Restart the Neo4j pod to refresh the
   synced Kubernetes Secret.

If the live password is lost, recovery means starting Neo4j with `dbms.security.auth_enabled=false`
(through `neo4j.config`, in-cluster only), running `ALTER USER neo4j SET PASSWORD '<new>'`, and
turning authentication back on; this has not been exercised. Nothing is stored in Neo4j yet, so a
fresh volume (delete the claim `data-exiqo-neo4j-0`, then start Neo4j with the current
`exiqo-neo4j-auth`) is the simple alternative today.

Deploy-step credentials: managed identities have no secret to rotate. A service principal secret
read from Key Vault is picked up by the next plan (it is never cached); see
`DEPLOY-STEP-SECRETS.md`.

## 11. Troubleshooting

Start with `kubectl -n exiqo get pods`, `kubectl -n exiqo describe pod <pod>` and
`kubectl -n exiqo logs <pod>`, and `GET /api/readyz`. It names the check that failed and its
exception class, never a value:

| Check | Meaning |
|---|---|
| `postgres: error: <class>` | the database is unreachable or refuses the login: firewall, NetworkPolicy, `postgres.cidrs`, a wrong password in `DATABASE_URL` |
| `secrets: error: unreadable <names>` | a `_FILE` secret is missing or unreadable: the CSI mount failed |
| `neo4j: down: <class>` | reported only; does not fail readiness |

| Symptom | Likely cause and where to look |
|---|---|
| Pod stuck in `ContainerCreating` with a mount error | The CSI driver cannot read Key Vault. `kubectl -n exiqo describe pod` shows the event. Check that `exiqo-platform` has Key Vault Secrets User, the federated credential's issuer and subject (`system:serviceaccount:exiqo:<account>`) match, `keyVault.name` and the object names are right, and the vault's firewall admits the cluster. |
| Install fails at the hook, Job `exiqo-migrate` times out | `kubectl -n exiqo logs job/exiqo-migrate`. Usually Postgres is unreachable (NetworkPolicy baseline, firewall, the `VECTOR` extension not allow-listed) or its secret did not mount. |
| `helm upgrade` rolled back (`--atomic`) | Run `helm history exiqo -n exiqo` and read the failed revision's hook and pod events; the cause is in the migration Job or a pod that never became ready. |
| StorageClass error at install | The deployer lacks cluster scope, or an upgrade changed an immutable parameter (section 6). |
| Sign-in redirects fail ("redirect URI mismatch", AADSTS50011) | The registered redirect URI is not exactly `https://<ingress.host>/api/auth/callback`. |
| "sign-in expired or was not started here" | The 10-minute login cookie was lost: sign-in was started on another host name, over http, or the page sat open too long. |
| "sign-in refused: wrong issuer" or "wrong audience" | `auth.tenantId` is not the tenant that issued the token, or it is a v1.0 token (section 3, token version), or the audience is not the client ID. |
| "Entra ID did not answer usably" (HTTP 502) | Egress to `login.microsoftonline.com` is blocked. |
| "your account holds no ExiQO Migrate role" (HTTP 403) | The user matches no entry of `auth.roleGroups`. Check the group object IDs or app role values; with many groups use app roles (group overage). Roles update at the next sign-in. |
| AADSTS50105 at sign-in | "Assignment required" is on and the user is not assigned to the application. |
| Calls to GMF mirrors, Azure OpenAI or Resource Manager time out | Egress denied: check the Azure Firewall rules for `egress.fqdns`, the NetworkPolicy (`egress.allowCidrs`, `egress.ports`) and private DNS. The About panel shows the allowlist the install believes in. |
| Restore fails with an NU1301 error | The NuGet mirror (`mirrors.nuget`) is unreachable or needs a host added to the firewall. |
| Plan fails with "Workload Identity is not configured for this pod" | The worker pod lacks the Workload Identity token (`AZURE_FEDERATED_TOKEN_FILE`): check the pod label `azure.workload.identity/use` and the add-on. |
| Plan fails with "deploy environment ... is no longer declared" | The environment is not in `deploy.environments`, or was renamed after the plan was queued. |
| Plan fails with an authorization error from Azure | The environment's identity lacks a role on the target subscription (`DEPLOY-STEP-SECRETS.md`), or the federated credential's subject does not name `exiqo-worker` in this namespace. |
| A job is stuck or reports "worker lost" | `RUNBOOK.md`, "A stuck job" and "worker lost". |
| Uploads fail on large estates | The ingress body limit (`ingress.api.annotations`) or, with AGIC, the gateway's WAF and request limits. |
